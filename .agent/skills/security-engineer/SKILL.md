# SECURITY_ENGINEER.MD

## 1. Executive Summary

**Obiettivo:** Garantire la confidenzialità dei dati sanitari (GDPR), l'integrità dei turni e la tracciabilità delle azioni amministrative.
**Approccio:** "Defense in Depth". La sicurezza è applicata a livello di Identità (Auth), Database (RLS) e Applicazione (Masking).
**Stato:** Approvato per sviluppo.

---

## 2. Identità e Accessi (IAM)

Abbandoniamo l'idea delle password condivise. Ogni utente è identificato univocamente.

* **Provider:** **Supabase Auth** (Email/Password).
* **Tier:** Free (fino a 50k MAU).
* **Politica di Registrazione:** **Invite Only**.
* Disabilitare "Open Sign-up" nel pannello Supabase.
* L'Admin crea manualmente le utenze per i collaboratori e invia le credenziali (o il magic link).


* **Ruoli Utente:**
* Useremo i "Custom Claims" o una tabella `profiles` collegata a `auth.users` per distinguere i ruoli.
* `admin`: Può scrivere su tutto.
* `observer`: Sola lettura, dati sanitari mascherati.

## 3. Database Hardening (Row Level Security)

Il database non si fida del frontend. Anche se un hacker bypassa l'interfaccia Streamlit, il database rifiuterà le scritture.

### Policy RLS (Da applicare in SQL)

```sql
-- Abilita RLS su tutte le tabelle critiche
ALTER TABLE roster ENABLE ROW LEVEL SECURITY;
ALTER TABLE employees ENABLE ROW LEVEL SECURITY;

-- 1. POLICY DI LETTURA (Tutti gli autenticati vedono i turni)
CREATE POLICY "Enable read access for all authenticated users"
ON roster FOR SELECT
TO authenticated
USING (true);

-- 2. POLICY DI SCRITTURA (Solo Admin)
-- Assumiamo che esista una tabella 'profiles' o un claim che identifica l'admin
-- Per MVP semplificato: L'email dell'admin è hardcodata o verificata
CREATE POLICY "Enable write access for admin only"
ON roster FOR ALL
TO authenticated
USING (auth.jwt() ->> 'email' = 'email.del.caposala@ospedale.it') -- Esempio MVP
WITH CHECK (auth.jwt() ->> 'email' = 'email.del.caposala@ospedale.it');

```

## 4. Data Privacy & Masking (GDPR Art. 9)

I dati sanitari non devono essere diffusi ingiustificatamente.

* **Regola di Visualizzazione (Frontend Logic):**
Quando Streamlit renderizza la griglia per un utente loggato come `Observer`:
* Se `shift_code` è `M` (Malattia) o `104` -> Mostrare visivamente `ASS` (Assenza generica) o un colore grigio neutro.
* Se `shift_code` è `F` (Ferie) o `P` (Permesso) -> Mostrare il codice reale (dato non sensibile).


* **Implementazione:**
La funzione Python `render_roster()` deve accettare il parametro `user_role`.
```python
# Pseudo-codice di sicurezza
if role != 'admin' and shift_code in ['M', '104']:
    display_code = 'ASS'
else:
    display_code = shift_code

```

## 5. Audit Logging (Tracciabilità)

Ogni modifica ai turni deve lasciare una traccia indelebile.

### Schema Tabella `audit_logs`

Da creare su Supabase tramite SQL Editor:

```sql
CREATE TABLE IF NOT EXISTS audit_logs (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id UUID REFERENCES auth.users(id), -- Chi ha fatto l'azione
    action_type TEXT NOT NULL, -- Es: 'UPDATE_SHIFT', 'GENERATE_ROSTER'
    target_resource TEXT, -- Es: 'Roster: Mario Rossi 25/10'
    old_value TEXT, -- Es: 'M'
    new_value TEXT, -- Es: 'N'
    timestamp TIMESTAMPTZ DEFAULT NOW()
);

-- RLS: Solo l'Admin può leggere i log. Nessuno può modificarli/cancellarli.
ALTER TABLE audit_logs ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Admin read logs" ON audit_logs FOR SELECT TO authenticated USING (auth.jwt() ->> 'email' = 'admin@email.it');
CREATE POLICY "System insert logs" ON audit_logs FOR INSERT TO authenticated WITH CHECK (true);

```

## 6. Sicurezza Applicativa (Streamlit)

### Gestione Segreti

* **Locale:** File `.streamlit/secrets.toml`. **MAI** committare su Git.
* **Produzione:** Usare il pannello "Secrets" di Streamlit Cloud.
* **Variabili Critiche:**
* `SUPABASE_URL`
* `SUPABASE_KEY` (Usare la `anon` key è OK se RLS è attiva, ma mai usare la `service_role` key nel frontend).



### Configurazione Produzione (`.streamlit/config.toml`)

Per evitare "Information Disclosure" in caso di crash:

```toml
[client]
showErrorDetails = false
toolbarMode = "viewer" # Nasconde menu sviluppatore agli utenti

```

## 7. Incident Response Plan (Flash)

Cosa fare se le cose vanno male:

1. **Sospetto Data Breach:** Revocare immediatamente le chiavi API dal pannello Supabase -> Settings -> API -> "Regenerate".
2. **Bug critico nel turno:** L'Admin deve avere una procedura di "Rollback" manuale (es. ripristinare il PDF stampato il giorno prima) mentre il sistema viene fixato.
3. **Account compromesso:** L'Admin può bloccare/bannare l'utente immediatamente dal pannello `Authentication` di Supabase.
